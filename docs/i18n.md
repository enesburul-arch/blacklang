# BlackLang I18n

BlackLang i18n separates generated UI text and display formatting from storage field names.

## Syntax

```black
i18n {
  default tr
  locales tr, en
}

label Product.name {
  tr "Ürün Adı"
  en "Product Name"
}

label app.title {
  tr "Depo"
  en "Warehouse"
}

label page.Products {
  tr "Ürünler"
  en "Products"
}

label action.create {
  tr "Oluştur"
  en "Create"
}

placeholder Product.name {
  tr "Ürün adını gir"
  en "Enter product name"
}

help Product.name {
  tr "Listelerde görünen ürün adı"
  en "Visible product name in lists"
}

message Product.stock {
  tr "Geçerli bir stok adedi gir"
  en "Enter a valid stock count"
}
```

## Rules

- Use one `i18n` block per project.
- `default` declares the initial locale used by generated web output.
- `locales` declares every locale accepted by translation blocks.
- The default locale must also be listed in `locales`.
- Top-level `label` blocks target stored fields and computed display fields with `Entity.field`.
- Top-level `label` blocks can also target generated UI copy with supported `app.*`, `page.*`, `action.*`, `table.*`, and `status.*` keys.
- Top-level `placeholder`, `help`, and `message` blocks target stored form fields with `Entity.field`.
- When more than one locale is declared, generated web UI includes a language selector.
- App chrome, navigation page names, table tools, status labels, CRUD buttons, custom action buttons, workflow transition buttons, and table/detail/form/filter/column labels re-render when the user changes locale.
- Form placeholders, form help text, and field-level frontend validation messages re-render when translated blocks exist.
- Table and detail values for `number`, `integer`, `decimal`, `money`, `date`, and `datetime` use `Intl` formatting for the active locale.
- The generated app shell adds `lang` and deterministic `dir` from the active locale. `ar`, `fa`, `he`, `ur`, and their region variants are RTL.
- If no runtime translation exists for the active locale, generated UI falls back to the default locale translation.
- If no translation exists, generated UI falls back to the matching field modifier such as `label "Text"`, `placeholder "Text"`, `help "Text"`, or `message "Text"`.
- If no field label modifier exists, generated UI falls back to title-cased field name.

## Current Scope

Draft v0.2 uses runtime translations for generated UI copy in:

- app shell title, menu, language selector, logout, navigation aria labels, auth-loading text, no-page text, and source/form dialog chrome
- navigation page names with `label page.<Page>`
- table search, filters, column chooser, pagination, empty table text, row selection aria labels, status/actions headers, and active/archive status text
- CRUD action buttons and form submit/cancel/close copy
- custom action buttons and panels with `label action.<CustomAction>`
- workflow transition buttons with `label action.<transition>`

Draft v0.2 also uses runtime translations for generated field labels in:

- table filter labels
- column visibility labels
- table headers
- detail panel labels
- form labels

Computed display field labels use the same `label Entity.computedField { ... }` shape.

Stored field placeholders, stored field help text, and stored field-level frontend validation messages use `placeholder Entity.field`, `help Entity.field`, and `message Entity.field`.

`message Entity.field` applies to generated frontend field-level validation for that stored field. Entity-level `validate ... message "Text"` remains explicit validation metadata in the current draft.

Currency formatting uses a deterministic locale-to-currency fallback table in generated React. Unknown locale/currency combinations fall back to USD for display.
